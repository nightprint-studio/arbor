# Bennu Framework-Awareness: Builtin vs Plugin Feasibility Report

> Generated by a multi-agent analysis workflow (baseline + 7 per-framework assessments +
> synthesis). Scope: should Spring, Struts 2, Lombok, MyBatis, Hibernate/JPA, Spring Data and
> Emmet awareness be **builtin** (Rust, in `crates/products/bennu/*`) or a **Lua plugin**?

## 1. Executive Summary

For every Java-semantic framework evaluated (Spring, Struts 2, Lombok, MyBatis, JPA/Hibernate,
Spring Data), the recommendation is **builtin**, and every one is **infeasible-as-plugin today**
for the same two structural reasons: bennu-be ships with *no plugin host at all* (`main.rs`
constructs `arbor_be::App` with no `plugin_host`/`NsHost`/`api_installer`), and even with a host
there is **no bidirectional code-intelligence contribution API** — no way to inject synthetic
symbols, virtual members, diagnostics, completions, references, or go-to resolvers into the
engine. The frameworks map almost perfectly onto machinery bennu *already owns natively*: the
`bennu-web` → `intel/config.rs` (`ingest_config_graph`) → `bennu-index` fst+blob store →
`ConfigResolver` pipeline that already delivers first-class Struts/Spring/Tiles cross-file
navigation and a deliberately conservative "action inesistente" diagnostic. Building framework
awareness as plugins would mean first constructing a whole plugin host *and* an unproven public
intel-contribution surface — strictly more work than extending the native pipeline, and slower,
with a lossier type model across the IPC/Lua boundary. **Emmet is the one outlier**: it is
orthogonal to all Java semantics (a pure JSP/HTML text transform), needs *none* of the index —
but as a plugin it would force building an editor-buffer/caret host API that doesn't exist, so it
too is builtin-first. The strategic play is: finish the frameworks natively on the existing
`config.rs` seam now, and extract a generic contribution SDK only *after* 2–3 native resolvers
exist to prove the trait shape.

## 2. Ranked Table

Ranked by leverage-to-effort: highest native reuse and lowest effort first.

| Framework | Builtin effort | Plugin feasibility | Recommendation | One-line why |
|---|---|---|---|---|
| **Struts 2** | medium | infeasible-as-plugin | **builtin** | Half already builtin (`struts.rs`+`ConfigResolver`); remaining OGNL/JSP/validation work needs deep CST+type-model access no plugin can reach. |
| **Lombok** | medium | infeasible-as-plugin | **builtin** | One clean injection point (`build_class_members`); only new ingredient is annotation extraction, then a mechanical synth pass; `@Builder` is the only medium part. |
| **Spring (core IoC)** | medium | infeasible-as-plugin | **builtin** | XML beans already ingested; only the annotation/type-wiring side is new, and it belongs next to the type resolver it depends on. |
| **Spring Data** | medium | infeasible-as-plugin | **builtin** | Derived-method-name grammar + `@Query` mini-parser over the existing entity type model; new code, no new architecture. |
| **MyBatis** | medium | infeasible-as-plugin | **builtin** | Structurally identical to the Struts action→class chain; bidirectional interface↔XML edge is the only richer bit. |
| **JPA / Hibernate** | **high** | infeasible-as-plugin | **builtin** | Same config-graph template, but JPQL/HQL is a real embedded grammar — the hard 30% — and hbm.xml-only entities need synthetic types. |
| **Emmet** | medium | infeasible-as-plugin | **builtin** | Orthogonal to all Java semantics; pure buffer text transform, but needs a live editor-buffer/caret write API that doesn't exist. |

## 3. The Shared "Code-Intelligence Plugin SDK"

This is the key strategic output. If bennu ever wants *third-party* framework packs (a niche
annotation dialect, a house-internal DSL), these are the generic `arbor.*` host extensions that
would unlock the most frameworks-as-plugins. **None of these should be built to ship the
frameworks below** — they are all better builtin — but this is the shape the SDK must take when a
genuine 2nd/3rd external consumer appears. Ranked by leverage (how many frameworks each unblocks ×
how irreplaceable it is).

### Prerequisite (gates everything): a bennu-be plugin host

Nothing below can exist until bennu-be has a Lua/WASM host + `NsHost` + `api_installer`, mirroring
what corvus-be did in `plugin_rpc.rs`. Today bennu-be runs zero plugins. This is a large,
standalone architectural investment and the single biggest cost of the entire plugin path.

### Leverage ranking of the SDK extensions

- **L1 — `arbor.intel.contribute_symbols` + `contribute_relations` (synthetic symbol/relation
  injection).** The highest-leverage primitive. A write path into the fst+blob symbol+relation
  stores lets a plugin inject scanned beans, `@Action`/annotation mappings, MyBatis statements,
  JPA entities, named queries — plus the edges (injection-point→bean, method→statement,
  entity→table) that go-to and find-usages traverse. **Every framework except Emmet needs this.**
  It is the plugin-side mirror of what `ingest_config_graph` does natively. Requires a new
  `Source::External`/`Plugin` variant. Without it, a plugin can parse config all day and has
  nowhere to put the result — it cannot make a single Ctrl+B work.
- **L2 — `arbor.intel.contribute_members` + `contribute_type` (virtual/generated member
  injection).** Augment a baked `ClassMembers` type with members that don't exist in source, and
  register whole synthetic types. **Unblocks Lombok entirely** (`getX`/`setX`/`builder()`/`log`,
  the `@Builder` nested type) and is a hard dependency for JPA (`@Data` entities), MyBatis
  (`resultMap`/`#{}` awareness), and Spring `@Value`/`@ConfigurationProperties`. The type model
  (`typemap.rs`) currently bakes members opaquely at ingest with **no augmentation seam**.
- **L3 — a parse/index lifecycle hook with CST access (`on_file_parsed` / `on_index_built`).**
  Every framework plugin needs to be *told* when to (re)scan, and needs read access to the
  tree-sitter CST or the extracted `FileSymbols`. The current hook catalog is **100%
  git/repo/workspace** — no editor/parse/index event exists. Must carry annotation *string
  arguments* (`@Component("x")`, `@Qualifier`, `@NamedQuery(name=...)`) or half the frameworks
  can't build their key set.
- **L4 — a string-embedded-DSL / go-to resolver registry (`register_string_region_resolver`).**
  A `ResolverProvider`-style trait so Ctrl+B *inside a string region* navigates: `@Qualifier("x")`,
  `ref="x"`, `${prop}`, `#{param}`, OGNL `%{...}`, JPQL `o.customer.name`, `@Query` literals.
  Today the `ActionTarget`/`ResultToView` chain is **hardcoded in `config.rs`** with no pluggable
  trait. Depends on L1 (can't resolve to a symbol that was never contributed).
- **L5 — `arbor.intel.publish_diagnostics` (diagnostics push channel).** Push
  `unsatisfied-bean`/`unknown-property`/`statement-without-method`/`unknown-entity` diagnostics
  into bennu-be's stream. Ranked lower because diagnostics are the last (and riskiest) feature.
- **L6 — a completion contribution seam (`register_completion_provider`).** Add candidates to the
  closed `completion()` fn: bean ids, property keys, result names, OGNL props, derived-method-name
  fields, `#{param}` names. Lowest of the semantic six because completion degrades gracefully.
- **L0 — (Emmet-only, disjoint) editor-buffer/caret read+write API
  (`arbor.editor.active/caret/get_text_around_caret/replace_range`).** A live-buffer mutation seam
  (tabstops, dirty-state, undo grouping) that unlocks *typing-accelerator* plugins, not code
  intelligence. High blast radius, needed by exactly one item on this list.

**Bottom line on the SDK:** L1 (symbol/relation contribution) + L3 (parse hook with annotated CST)
together unblock the *most* frameworks; L2 (member injection) is the differentiator that makes
Lombok/JPA viable at all. If ever built, build it in that order, against **≥2 already-working
native resolvers** so the trait shape is proven, not guessed.

## 4. Per-Framework Detail

**Struts 2 — builtin (medium).** Half already ships: `bennu-web` parses `struts.xml`
include-graphs, wildcards and `{n}` backrefs; `ConfigResolver` serves the C1 action→bean→FQCN
chain, the Tiles view chain, and a conservative `diagnose_action`. Remaining — OGNL value-stack
resolution, real JSP/TLD parsing (`bennu-jsp` is a Phase-0 skeleton), interceptors,
`validation.xml`, `@Action`/Convention annotations — needs deep CST+`ClassMembers` access no
plugin has. The OGNL value-stack resolver (root object changes per action) is the genuinely hard
part.

**Lombok — builtin (medium, mostly low).** Single clean injection point:
`java_index.rs::build_class_members`, which already has the field list, imports and project types;
anything appended there flows through the index into completion/hover/go-to/refs unchanged. The
only new ingredient is **annotation extraction in `symbols.rs`** (which today reads `modifiers`
for keywords only and ignores annotation nodes). Given that, `@Getter/@Setter/@Data/@Value/@Slf4j`
+constructors are a mechanical synth pass; `@Builder` pushes it to medium (a synthetic nested
`FooBuilder` type + go-to redirection). Watch `@Accessors(fluent)`, boolean `isX` prefixes, and
`lombok.config` overrides.

**Spring (core IoC) — builtin (medium).** XML beans already ingested; the new work is the
**annotation side**: derive the scanned-bean set from `@Component`/`@Bean`+component-scan, add a
**type-assignability** wiring resolver for `@Autowired`/`@Qualifier`/`@Primary` (resolves by
assignable type, not literal id), a properties/YAML value graph for `@Value`/`${...}`, and reuse
the conservative-diagnostic pattern for unsatisfied/ambiguous beans. Top risk is false-positive
diagnostics (beans from jars, `@Import`, `@Conditional`/profiles) — must follow `diagnose_action`'s
"Inconclusive, never Missing" discipline.

**Spring Data — builtin (medium).** Needs three things over the existing entity model: resolve the
repository's domain type off `JpaRepository<Foo, Long>` generics, a **derived-method-name parser**
(`findBy…And…OrderBy…`, ~20 keyword suffixes, greedy property paths), and a `@Query` JPQL/param
mini-parser. `ClassMembers{fields}` already answers "does entity Y have field X." The PartTree
grammar is deceptively large; stay `Inconclusive` on ambiguous property paths.

**MyBatis — builtin (medium).** Structurally identical to the Struts action→class chain:
`<mapper namespace="…FooMapper">` binds the file to an interface FQCN, each `<select id="bar">` is
`Foo.bar`. Copy the template: a `bennu-mybatis` parse crate, extend ingest with
`Source::MyBatisMapper`/`RelationKind::MethodToStatement`, a `MyBatisResolver` with bidirectional
method↔statement go-to and a conservative orphan diagnostic. The bidirectional edge is richer than
the one-way action→class chain (relation store is out-edge-keyed today, so reverse lookup needs a
second set).

**JPA / Hibernate — builtin (high).** Same config-graph template, but the highest effort because
**JPQL/HQL is a real embedded grammar** (path expressions, aliases, joins, named params,
subqueries). Also needs synthetic type/member symbols for `hbm.xml`-only entities that have no
`.java` decl site, and couples to the Lombok member-augmentation work (`@Data` entities). Scope the
MVP to entity-name + top-level `alias.field` resolution first; skip-don't-flag native SQL. JPA
should be the *second native proof* of the resolver shape.

## 5. Emmet Callout

**Emmet is not a framework-awareness feature — it is a JSP/HTML typing accelerator.** It expands a
CSS-selector-like abbreviation (`ul>li*3>a` → nested markup; `>` child, `+` sibling, `^` climb,
`*N` multiply, `()` group, `#id`, `.class`, `[attr=val]`, `{}` text, `$` numbering) with
implicit-tag inference. It touches **none** of bennu's engine surface: no symbol index, no type
resolver, no reference walk, no config graph, no diagnostics, no completion, no go-to.

In most editors Emmet *is* a trivial plugin — a buffer text transform bound to Tab/Ctrl+E. **But in
bennu it is infeasible-as-plugin for the inverse reason from the frameworks**: it needs none of the
*semantic* host API, yet it needs a **live editor-buffer + caret read/write seam** the plugin host
lacks entirely (`arbor.text` is regex string helpers only; `arbor.fs.write` mutates disk and would
fight dirty-state/caret). **Call: builtin (medium)**, a native command gated to `.jsp/.html/.xml`,
bound to Tab/Ctrl+E — the editor already owns buffer/caret/undo natively, which is exactly why
builtin wins (correct caret/tabstop placement is the fiddly part). Do **not** let Emmet be the
forcing function for the editor-buffer host API. Ship an HTML/JSP markup subset first; defer CSS
abbreviations, filters, lorem, custom snippets.

## 6. Recommended Phased Roadmap

### Phase 1 — Build builtin now, on the existing native seam (no host, no SDK)

1. **Annotation extraction in `bennu-java/symbols.rs`** — surface class+member annotations *with
   string arguments*. Shared prerequisite for Lombok, Spring, Spring Data and JPA; do it once, first.
2. **Lombok** — the mechanical synth pass at `build_class_members`. Lowest effort, immediately
   visible (getters/setters/`@Data`/`@Slf4j`); member-synthesis also feeds JPA/Spring `@Value`.
   `@Builder` last.
3. **MyBatis** — copy the Struts template (`Source::MyBatisMapper`, `MethodToStatement`,
   bidirectional resolver + reverse index).
4. **Spring core IoC** — scanned-bean set + type-assignability wiring resolver + properties/YAML
   value graph. Reuses the annotation work from step 1.
5. **Spring Data** — derived-method-name parser + `@Query` mini-parser over the richer entity model.
6. **Struts 2 completion** — OGNL value-stack resolver, real JSP/TLD parse, `validation.xml`,
   `@Action` annotations. Highest remaining native effort.
7. **JPA / Hibernate** — highest effort; MVP scoped to entity-name + top-level `alias.field`.
8. **Emmet** — independent, parallelizable any time; native command gated to markup buffers.

**Non-negotiable across all of these:** every new diagnostic must follow the `diagnose_action`
**"Inconclusive, never Missing"** conservatism, or it will scream on real legacy Entando/Struts
trees.

### Phase 2 — Build the host-API first-mover *only when a real external need appears*

Do **not** build the SDK to ship any of the above. Once ≥2 native resolvers exist (after Phase 1),
they become the two concrete impls that prove the trait shape. Build in leverage order:
(a) bennu-be plugin host (prerequisite, mirrors corvus-be `plugin_rpc.rs`), (b) L3 parse/index
hook with annotated CST, (c) L1 `contribute_symbols`/`contribute_relations` (new `Source::Plugin`
variant), (d) L2 `contribute_members`/`contribute_type`, (e) L4 string-region resolver registry,
(f) L5/L6 diagnostics + completion push.

### Phase 3 — Defer

- The editor-buffer/caret write API (L0) unless/until user-authored Emmet snippets or a broader
  typing-accelerator plugin class is wanted — disjoint from code intelligence, high blast-radius.
- Entando/jAPS resolver — currently only capability-detected; ride the same seam once the core
  frameworks are done.
- Freezing *any* public `arbor.intel.*` contract before ≥2 native consumers exist.

**One-line strategic verdict:** every framework is builtin-first; the shared SDK (host + L1
symbol/relation contribution + L3 annotated parse hook + L2 member injection) is real and worth
designing — but only *after* the native resolvers exist to prove its shape, never as the vehicle
to ship the first framework.
